# E12.04 Prepayment Settlement Implementation Plan

> **For agentic workers:** Follow this plan task-by-task. Each task is a review checkpoint; do not run migrations against Supabase or commit changes.

**Goal:** Record a pre-dispatch advance, allocate only the amount of the completed fuel sale, and leave the unused balance pending until an authorized per-case refund/release is confirmed.

**Architecture:** Add an append-only prepayment ledger separate from sale-scoped `payment_attempts`. Link each tender to an existing dispense authorization; create allocations only to a sale created from completed measured dispense. Keep residual state within C07’s `refundPending`, `refunded`, and `released` vocabulary, and route refunds through existing approval controls. Neither retries nor financial settlement may repeat the sale or change physical inventory.

**Tech Stack:** PostgreSQL migration (authored, never applied in this task), NestJS/TypeScript, existing `pg` pool, class-validator DTOs, Node test runner with stubbed repositories, OpenAPI JSON.

## Confirmed interfaces and constraints

- `server/src/sales/payments.controller.ts` protects collection with `payment.collect`; resolution uses `payment.resolve`; refund request/approval/execution use `sale.refund.request`, `approval.decide`, and `payment.refund`; cash actions retain their existing `cash.*` permissions.
- `server/src/sales/payments.service.ts` owns command hashing, idempotency, audit and cash/event writes. It currently requires `sale_id` for a `payment_attempt`; therefore an advance stores its original tender fields (`method`, `mode`, `cash_session_id`, documentary reference) directly instead of pretending to reference a sale-scoped payment attempt.
- `server/src/sales/sales.service.ts:createFuelSale` creates a sale only when its dispense authorization is `completed`, and replays by `commandId` without another sale.
- `server/src/infrastructure/infrastructure.service.ts` maintains dispense authorization and recovery. `unknown` is reconciled against the original authorization; it is not a no-flow fact.
- Existing suites are `server/test/payments-service.test.mjs`, `server/test/contracts/payments-contract.test.mjs`, `server/test/dispense-device-service.test.mjs`; there is no existing prepayment service test.
- User-approved policy: each remainder requires an explicit per-case disposition, constrained by recorded tender kind. `captured` funds can be refunded; only a confirmed manual card `authorization_hold` can be released. This is not an automatic method default. Existing `confirmed`/`declined`/`unknown` outcomes are preserved; unknown retains the amount and blocks cash-session closure. Terminal states require matching evidence. Physical inventory correction stays separate.
